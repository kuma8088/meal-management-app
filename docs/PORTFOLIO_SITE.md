## プロジェクト概要

### LINE × Web ハイブリッド食事管理システム

日常的に使う **LINE** から食事を記録し、**AI** がパーソナライズされた栄養アドバイスを提供するヘルスケアアプリケーション。

| 項目 | 内容 |
|:-----|:-----|
| 開発期間 | 約2週間 |
| 担当領域 | 設計 / バックエンド / フロントエンド / インフラ（フルスタック） |
| 開発体制 | 個人開発 |

## このプロジェクトで解決した課題

### Before: 従来の食事管理の課題

| 課題 | 詳細 |
|:-----|:-----|
| 手入力の煩雑さ | 毎食の記録が面倒で継続率が低い |
| 栄養計算の複雑さ | カロリー・PFCを自分で調べて計算する必要がある |
| チャネルの分断 | スマホアプリとWebで別々に管理 |
| 運用コストの不透明さ | 常時稼働サーバーの月額費用が読めない |

### After: 本システムによる解決

| 解決策 | 効果 |
|:-------|:-----|
| バーコード撮影で即記録 | 入力時間 5分 → **30秒**に短縮 |
| 2,538品目の自動栄養計算 | 日本食品標準成分表準拠の正確なデータ |
| LINE + Web 統合 | どちらからでも同じデータにアクセス |
| 完全サーバレス | 使った分だけの課金、**固定費ゼロ** |

## Amazon Bedrock（Claude 3）の活用

### Bedrockを呼び出す3つのタイミング

本システムでは、以下の3つのタイミングでAmazon Bedrockを呼び出しています。

| # | タイミング | モデル | 用途 |
|:--|:-----------|:-------|:-----|
| 1 | 食品検索フォールバック | Claude 3 Sonnet | 未登録食品の栄養情報推定 |
| 2 | 日次アドバイス | Claude 3 Haiku | 1日の食事記録に基づくアドバイス |
| 3 | 週次レポート | Claude 3 Haiku | 7日間の統計に基づく振り返り |

#### 1. 食品検索のフォールバック

ユーザーが食品名を入力した際、DynamoDBに該当食品がない場合にBedrockで栄養情報を推定生成。

```
[ユーザー入力: 「鶏むね肉のソテー」]
        |
        v
+------------------------+
| DynamoDB 検索          |
| (食品マスタ 2,538品目  |
|  + AIキャッシュ)       |
+------------------------+
        |
   Hit? |
        +-- Yes --> [即座に返却: 50ms]
        |
        +-- No ---> Bedrock Claude Sonnet 呼び出し
                           |
                           v
                    [S3の食品CSVを参照しAIが栄養情報を推定: 2-3秒]
                           |
                           v
                    [DynamoDB にキャッシュ保存（AI_GENERATEDフラグ付き）]
                           |
                           v
                    [次回以降は DynamoDB から返却]
```

#### 2. 日次アドバイス（1日2回まで）

ユーザーの1日の食事記録と目標値を基に、AIがアドバイスを生成。

```
[トリガー]
  - Web: 「AIアドバイス」ボタン押下
  - LINE: 「アドバイス」「総評」とメッセージ送信

        |
        v
+------------------------+
| 利用回数チェック       |
| (1日2回まで)           |
+------------------------+
        |
        v
+------------------------+
| DynamoDB から取得      |
| - 当日の食事記録       |
| - 目標カロリー         |
| - PFCバランス          |
+------------------------+
        |
        v
+------------------------+
| Bedrock Claude Haiku   |
| プロンプト:            |
| - 摂取カロリー vs 目標 |
| - PFCバランス評価      |
| - 300文字以内で出力    |
+------------------------+
        |
        v
[パーソナライズされたアドバイスを返却]

例: 「本日のタンパク質摂取量は目標の65%です。
     夕食に鶏むね肉や豆腐を加えることをお勧めします。」
```

#### 3. 週次レポートアドバイス

7日間の統計データを基に、1週間の振り返りアドバイスを生成。

```
[トリガー]
  - EventBridge: 毎週日曜 21:00 に自動実行
  - Web/LINE: 「週次レポート」リクエスト

        |
        v
+------------------------+
| DynamoDB から集計      |
| - 過去7日間の食事記録  |
| - 平均カロリー/日      |
| - 平均タンパク質/日    |
| - 目標達成日数 (x/7日) |
+------------------------+
        |
        v
+------------------------+
| Bedrock Claude Haiku   |
| プロンプト:            |
| - 週間平均 vs TDEE     |
| - 目標達成率           |
| - 励ましと改善提案     |
| - 300文字以内で出力    |
+------------------------+
        |
        v
[週次アドバイスを LINE Push / Web表示]

例: 「今週は7日中5日で目標カロリーを達成できました！
     週末の外食時にタンパク質が不足気味でした。
     外食時は焼き鳥や刺身を選ぶと改善できます。」
```

## 技術的な差別化ポイント

### 1. AIコスト70-80%削減のキャッシング戦略

**課題**: Bedrock API は呼び出しごとに課金 → 頻繁に検索される食品で無駄なコスト

**解決策**: AI生成結果をDynamoDBにキャッシュし、2回目以降はAPIを呼び出さない

| 検索パターン | レスポンス | Bedrock呼び出し |
|:-------------|:-----------|:----------------|
| 食品マスタにヒット | 50ms | なし |
| AIキャッシュにヒット | 50ms | なし |
| 初回AI生成 | 2-3秒 | あり |

**成果**: 同一食品の再検索時、**API呼び出しゼロ**でレスポンス → コスト70-80%削減

### 2. プロパティベーステストによる品質保証

#### なぜプロパティテストを採用したか

栄養計算の精度はユーザーの健康に直結するため、**従来のユニットテストでは不十分**と判断。

| テスト手法 | 特徴 | 本プロジェクトでの課題 |
|:-----------|:-----|:-----------------------|
| ユニットテスト | 特定の入力値で検証 | 境界値やエッジケースの網羅が困難 |
| **プロパティテスト** | **ランダム入力で数学的性質を検証** | **あらゆる入力パターンを自動探索** |

例えば「カロリー計算が正しいか」を検証する場合：
- ユニットテスト: `calculate_calories(rice_100g) == 168` のような固定値テスト
- プロパティテスト: **「任意の食品リストに対して、合計カロリー = 各食品のカロリー総和」** という性質を検証

#### 26個のプロパティ（4カテゴリ）

| カテゴリ | プロパティ数 | 検証内容 |
|:---------|:------------:|:---------|
| **栄養計算の正確性** | 8 | 加算性、非負性、単位変換の整合性 |
| **生理指標の妥当性** | 6 | BMR/TDEE計算、目標設定の範囲チェック |
| **データ整合性** | 7 | ユーザー間の分離、日付境界処理 |
| **API契約** | 5 | リクエスト/レスポンス形式の保証 |

#### プロパティの具体例

```
【栄養計算の加算性】
任意の食品リスト foods に対して:
  sum([f.calories for f in foods]) == calculate_total(foods).calories

  → 100種類のランダム食品組み合わせで自動検証
```

```
【BMR計算の単調性】
同一人物の体重が増加した場合:
  BMR(weight=70kg) < BMR(weight=75kg)

  → 体重30kg〜150kgの範囲で自動検証
```

```
【ユーザーデータ分離】
異なるユーザーID間で:
  get_meals(user_A) ∩ get_meals(user_B) == ∅

  → ランダム生成したユーザーペアで自動検証
```

#### 検出したバグ3件

プロパティテストにより、手動テストでは発見困難だったバグを自動検出。

| # | バグ内容 | 発見したプロパティ | 影響 |
|:--|:---------|:-------------------|:-----|
| 1 | **浮動小数点の丸め誤差** | 栄養値の加算性 | 100品目以上の合計で0.1kcal程度の誤差が蓄積 |
| 2 | **日付境界の処理漏れ** | データ整合性 | 23:59:59に登録した食事が翌日扱いになるケース |
| 3 | **BMR計算の年齢境界** | 生理指標の妥当性 | 年齢0歳・150歳などの極端値で計算式が破綻 |

#### テスト結果

| 指標 | 数値 |
|:-----|-----:|
| 正確性プロパティ | 26個 |
| テストケース生成数 | 約10,000件/実行 |
| コードカバレッジ | **85%** |
| バグ検出数 | 3件 |

#### ビジネス価値

| 効果 | 詳細 |
|:-----|:-----|
| **品質保証** | 栄養計算の信頼性を数学的に担保 |
| **リグレッション防止** | 機能追加時も既存ロジックの破壊を自動検知 |
| **エッジケース網羅** | 手動では思いつかない境界条件を自動探索 |
| **ドキュメント効果** | プロパティ定義がシステム仕様書として機能 |

### 3. VPC不要のコスト最適化設計

**従来のサーバレス構成の課題**:  
Lambda から DynamoDB にアクセスするために NAT Gateway が必要 → **月額 $32〜** の固定費

**本プロジェクトの解決策**:  
全 AWS サービスをパブリックエンドポイント経由で利用 → **固定費ゼロ**

```
従来の構成                    本プロジェクトの構成
==========                    ====================

Lambda --> VPC --> NAT GW     Lambda --> Public Endpoint
       --> DynamoDB                  --> DynamoDB

固定費: $32+/月               固定費: $0
```

#### VPC が必要なケース vs 不要なケース

| 要件 | VPC必要 | VPC不要（本PJ） |
|:-----|:-------:|:---------------:|
| RDS / ElastiCache を使用 | ✅ | - |
| オンプレミス・VPN接続 | ✅ | - |
| 外部API連携で固定IP必要 | ✅ | - |
| 金融・医療レベルのコンプライアンス | ✅ | - |
| DynamoDB / S3 / Cognito のみ | - | ✅ |
| IAMポリシーで十分なアクセス制御 | - | ✅ |
| 個人開発・スタートアップ初期 | - | ✅ |

#### 本プロジェクトでVPC不要と判断した理由

| 判断ポイント | 本プロジェクトの状況 |
|:-------------|:---------------------|
| **使用サービス** | DynamoDB, S3, Cognito, Bedrock → 全てパブリックエンドポイント対応 |
| **アクセス制御** | IAMポリシー + Cognito認証で十分 |
| **データ機密性** | 個人の食事記録（中程度）→ 金融・医療レベルではない |
| **外部連携** | LINE API → 固定IP不要（Webhook受信のみ） |
| **コスト優先度** | 個人開発 → 固定費ゼロが最優先 |

#### VPCを採用すべきケースの例

```
【ケース1: 金融系アプリ】
要件: PCI DSS準拠、監査ログ、ネットワーク分離
  → VPC + Private Subnet + VPC Flow Logs 必須

【ケース2: 社内システム連携】
要件: オンプレDBとのデータ同期
  → VPC + Site-to-Site VPN or Direct Connect 必須

【ケース3: 外部SaaS連携】
要件: 連携先がIP制限をかけている
  → VPC + NAT Gateway（固定IP）必須
```

**結論**: VPC不要は「コスト削減のため」ではなく、**要件を満たしつつ最もシンプルな構成**を選択した結果

### 4. Lambda vs ECS の選択

**なぜ ECS/Fargate ではなく Lambda を選んだのか？**

サーバレスといえば Lambda が定番だが、**ECS/Fargate の方が適切なケースも多い**。本プロジェクトでは要件を精査した上で Lambda を選択。

#### Lambda と ECS/Fargate の特性比較

| 特性 | Lambda | ECS/Fargate |
|:-----|:-------|:------------|
| **課金モデル** | 実行時間（ms単位） | 起動時間（秒単位） |
| **最小コスト** | $0（無料枠内） | ~$13/月（最小構成） |
| **コールドスタート** | あり（100ms〜数秒） | なし（常時起動可） |
| **実行時間上限** | 15分 | 無制限 |
| **メモリ上限** | 10GB | 30GB（Fargate） |
| **同時実行** | 1リクエスト=1インスタンス | 1コンテナで複数リクエスト |
| **ステートフル処理** | 困難 | 可能 |

#### Lambda が適しているケース（本プロジェクト）

| 要件 | 本プロジェクトの状況 | Lambda適性 |
|:-----|:---------------------|:----------:|
| **トラフィックパターン** | 散発的（食事記録時のみ） | ✅ |
| **処理時間** | 数秒以内（API呼び出し） | ✅ |
| **リクエスト単位の独立性** | 各記録は独立、状態共有不要 | ✅ |
| **スケール要件** | 急なスパイクなし | ✅ |
| **コスト優先度** | 固定費ゼロが最優先 | ✅ |

#### ECS/Fargate を選ぶべきケース

```
【ケース1: 長時間バッチ処理】
要件: 数時間かかるデータ処理、ML推論
  → Lambda 15分制限に抵触 → ECS/Fargate or Step Functions

【ケース2: 常時接続が必要】
要件: WebSocket、gRPC、ストリーミング
  → Lambda はリクエスト/レスポンス型 → ECS/Fargate + ALB

【ケース3: 高頻度・低レイテンシ】
要件: 秒間1000リクエスト以上、50ms以内のレスポンス必須
  → コールドスタートが許容できない → ECS/Fargate（常時起動）

【ケース4: 大規模モノリス移行】
要件: 既存アプリのコンテナ化、段階的移行
  → Lambda への分割コストが高い → ECS/Fargate でリフト

【ケース5: GPUが必要】
要件: リアルタイム画像処理、ML推論
  → Lambda は GPU非対応 → ECS on EC2（GPU インスタンス）
```

#### 本プロジェクトの判断フロー

```
Q1: 処理時間は15分以内？
    → Yes（API呼び出し数秒）

Q2: コールドスタートは許容できる？
    → Yes（食事記録にリアルタイム性不要）

Q3: トラフィックは散発的？
    → Yes（1日数回の記録）

Q4: 固定費ゼロが重要？
    → Yes（個人開発）

→ 全てYes → Lambda が最適
```

#### 将来的に ECS 移行を検討するケース

| シナリオ | 移行理由 |
|:---------|:---------|
| ユーザー数が1万人超え | Lambda同時実行制限、コスト逆転 |
| リアルタイム機能追加 | WebSocket対応が必要 |
| ML推論の高度化 | GPU必要、処理時間増大 |
| マルチテナント化 | コンテナ分離でセキュリティ強化 |

**結論**: Lambda は「サーバレスだから」ではなく、**散発的なトラフィック・短時間処理・固定費ゼロ**という要件に最適だったため選択

#### 認証方式

```
┌─────────────────────────────────────────────────────────────┐
│                    API Gateway 認証フロー                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [Web App]                         [LINE Bot]               │
│      |                                  |                   │
│      | Authorization: Bearer {JWT}      | X-Line-Signature  │
│      v                                  v                   │
│  +------------------+           +------------------+        │
│  | Cognito          |           | Lambda内で       |        │
│  | Authorizer       |           | 署名検証         |        │
│  +------------------+           +------------------+        │
│      |                                  |                   │
│      | user_id をコンテキストに注入      | line_user_id 取得 │
│      v                                  v                   │
│  +------------------+           +------------------+        │
│  | Lambda 関数      |           | Lambda 関数      |        │
│  | (認証済み)       |           | (署名検証済み)   |        │
│  +------------------+           +------------------+        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

| 認証方式 | 対象エンドポイント | 検証方法 |
|:---------|:-------------------|:---------|
| **Cognito Authorizer** | `/foods/*`, `/meals/*`, `/goals`, `/advice`, `/users/*`, `/summary/*` | JWT トークン検証、`user_id` をLambdaに渡す |
| **LINE署名検証** | `/webhook/line` | `X-Line-Signature` ヘッダーをLambda内で検証 |

#### JWT（JSON Web Token）によるステートレス認証

**なぜ Cognito + JWT を採用したか**

サーバレス環境では Lambda が毎回異なるインスタンスで起動するため、従来のセッションベース認証（サーバー側でログイン状態を保持）は不向き。JWT はトークン自体にユーザー情報を含むため、サーバー側で状態を持たずに認証が完結する。

```
┌─────────────────────────────────────────────────────────────┐
│                    JWT の構造（3パート）                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  eyJhbGciOiJSUzI1NiJ9.eyJ1c2VyX2lkIjoiYWJjLTEyMyJ9.xxxxx   │
│  ├─────────────────┤ ├─────────────────────────┤ ├─────┤   │
│        Header              Payload              Signature   │
│                                                             │
│  ┌─────────────┐    ┌─────────────────────┐    ┌─────────┐ │
│  │ アルゴリズム │    │ ユーザー情報        │    │ 署名    │ │
│  │ {"alg":     │    │ {"user_id": "xxx",  │    │ 改ざん  │ │
│  │  "RS256"}   │    │  "email": "...",    │    │ 検知用  │ │
│  │             │    │  "exp": 1234567890} │    │         │ │
│  └─────────────┘    └─────────────────────┘    └─────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**認証フローとユーザーデータ分離**

```
1. ログイン
   User → Cognito: メール/パスワード認証
   Cognito → User: JWT発行（user_id埋め込み）

2. API呼び出し
   User → API Gateway: Authorization: Bearer {JWT}
   API Gateway → Cognito Authorizer: トークン検証
   Cognito Authorizer: 署名OK? 有効期限OK? 改ざんなし?
   API Gateway → Lambda: user_id をコンテキストに注入

3. データアクセス（ユーザー分離の実現）
   Lambda: user_id = event.requestContext.authorizer.claims.sub
   Lambda → DynamoDB: Query(PK = user_id)
   → 自分のデータのみ取得、他ユーザーのデータには絶対にアクセス不可
```

| 観点 | セッション認証 | JWT認証（本システム） |
|:-----|:---------------|:----------------------|
| 状態管理 | サーバー側で保持 | トークン内に含む（ステートレス） |
| スケーラビリティ | セッションストア必要 | 不要（Lambda向き） |
| サーバー再起動 | セッション消失リスク | 影響なし |
| データ分離 | セッションIDで識別 | JWT内のuser_idで確実に分離 |

**トークンの有効期限とリフレッシュ**

Cognito は2種類のトークンを発行し、セキュリティと利便性を両立：

| トークン種別 | 有効期限 | 用途 |
|:-------------|:---------|:-----|
| **ID Token** | 1時間 | API認証（`Authorization` ヘッダーに付与） |
| **Refresh Token** | 30日 | ID Token の再発行（ユーザー操作不要で自動更新） |

```
┌─────────────────────────────────────────────────────────────┐
│                  トークンリフレッシュフロー                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [初回ログイン]                                              │
│  User → Cognito: 認証情報送信                                │
│  Cognito → User: ID Token (1h) + Refresh Token (30d) 発行   │
│                                                             │
│  [1時間後: ID Token 期限切れ]                                │
│  User → Cognito: Refresh Token 送信                         │
│  Cognito → User: 新しい ID Token (1h) 発行                  │
│  → ユーザーは再ログイン不要で継続利用可能                     │
│                                                             │
│  [30日後: Refresh Token 期限切れ]                            │
│  User → Cognito: Refresh Token 送信                         │
│  Cognito → User: エラー（要再ログイン）                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**JWT のセキュリティ考慮事項**

| リスク | 対策 | 本システムでの実装 |
|:-------|:-----|:-------------------|
| **XSS攻撃** | トークンをJSからアクセス不可にする | `localStorage` 使用（※後述） |
| **トークン漏洩** | 有効期限を短く設定 | ID Token: 1時間 |
| **CSRF攻撃** | トークンをCookieではなくヘッダーで送信 | `Authorization: Bearer` ヘッダー |
| **改ざん** | 署名検証 | Cognito が RS256 で署名検証 |

**localStorage vs HttpOnly Cookie の選択**

| 保存場所 | XSS耐性 | CSRF耐性 | 実装難易度 |
|:---------|:-------:|:--------:|:----------:|
| `localStorage` | △ | ◎ | 低 |
| `HttpOnly Cookie` | ◎ | △ | 高 |

本システムでは `localStorage` を採用。理由：
1. **CSRF対策が不要**: トークンは `Authorization` ヘッダーで送信するため、Cookie自動送信によるCSRFリスクなし
2. **XSS対策**: React の自動エスケープ + Content Security Policy で軽減
3. **実装シンプル**: HttpOnly Cookie はサーバー側でのCookie設定が必要で、Lambda + API Gateway 構成では複雑化

#### CORS 設定

**なぜ CORS が必要か？**

ブラウザには **Same-Origin Policy（同一オリジンポリシー）** というセキュリティ機構があり、異なるドメインへのリクエストをデフォルトでブロックする。

```
┌─────────────────────────────────────────────────────────────┐
│              Same-Origin Policy とは                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [同一オリジン = プロトコル + ホスト + ポート が一致]         │
│                                                             │
│  https://app.example.com:443                                │
│  ├────┤ ├──────────────┤ ├─┤                                │
│  Protocol    Host        Port                               │
│                                                             │
│  ✅ 許可: https://app.example.com → https://app.example.com │
│  ❌ 拒否: https://app.example.com → https://api.example.com │
│           （ホストが異なる = クロスオリジン）                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

本システムでは、フロントエンド（CloudFront）と API（API Gateway）が異なるドメインのため、CORS 設定が必須。

```hcl
# Terraform での CORS 設定
Access-Control-Allow-Origin:  "https://app.example.com"
Access-Control-Allow-Methods: "GET, POST, PUT, DELETE, OPTIONS"
Access-Control-Allow-Headers: "Content-Type, Authorization"
```

| 設定項目 | 値 | 理由 |
|:---------|:---|:-----|
| Allow-Origin | 本番ドメインのみ | セキュリティ（`*` は使用しない） |
| Allow-Methods | 必要なメソッドのみ | 最小権限の原則 |
| Allow-Headers | `Authorization` 必須 | Cognito JWT トークン送信用 |

**プリフライトリクエスト（OPTIONS）**

ブラウザは「単純でないリクエスト」を送信する前に、サーバーに許可を確認する **プリフライトリクエスト** を自動送信する。

```
┌─────────────────────────────────────────────────────────────┐
│              プリフライトリクエストの流れ                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [単純でないリクエストの条件]                                 │
│  - Content-Type が application/json                         │
│  - カスタムヘッダー（Authorization）を含む                   │
│  - PUT/DELETE メソッド                                      │
│  → 本システムの API は全てこれに該当                         │
│                                                             │
│  [フロー]                                                    │
│  Browser → API Gateway: OPTIONS /meals (プリフライト)       │
│  API Gateway → Browser: 200 OK + CORS ヘッダー              │
│  Browser: 「許可された！本番リクエスト送信OK」               │
│  Browser → API Gateway: POST /meals (本番リクエスト)        │
│  API Gateway → Browser: 201 Created                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**本システムでの OPTIONS 対応**

API Gateway REST API では、各エンドポイントに OPTIONS メソッドを設定し、Lambda を経由せずに直接 CORS ヘッダーを返す（Mock Integration）。これにより：
- Lambda のコールドスタートを回避
- プリフライトのレスポンス時間を最小化（〜10ms）

```hcl
# Terraform: OPTIONS メソッドの Mock Integration
resource "aws_api_gateway_integration" "options" {
  rest_api_id = aws_api_gateway_rest_api.main.id
  resource_id = aws_api_gateway_resource.meals.id
  http_method = "OPTIONS"
  type        = "MOCK"  # Lambda を経由しない

  request_templates = {
    "application/json" = "{\"statusCode\": 200}"
  }
}
```

#### レスポンス形式（統一フォーマット）

**成功時**
```json
{
  "statusCode": 200,
  "body": {
    "data": { ... },
    "message": "Success"
  }
}
```

**エラー時**
```json
{
  "statusCode": 400,
  "body": {
    "error": {
      "code": "VALIDATION_ERROR",
      "message": "カロリーは0以上の数値を指定してください",
      "details": { "field": "calories", "value": -100 }
    }
  }
}
```

#### エラーコード体系

| HTTPステータス | エラーコード | 発生条件 |
|:--------------:|:-------------|:---------|
| 400 | `VALIDATION_ERROR` | リクエストパラメータ不正 |
| 400 | `INVALID_FOOD_ID` | 存在しない食品ID |
| 401 | `UNAUTHORIZED` | JWT トークン無効・期限切れ |
| 403 | `FORBIDDEN` | 他ユーザーのリソースへのアクセス |
| 404 | `NOT_FOUND` | リソースが存在しない |
| 429 | `RATE_LIMIT_EXCEEDED` | AIアドバイス利用上限（1日2回） |
| 500 | `INTERNAL_ERROR` | サーバー内部エラー |
| 503 | `BEDROCK_UNAVAILABLE` | Bedrock API 一時的エラー |

#### API Gateway の設計判断

**REST API vs HTTP API の選択**

| 項目 | REST API（採用） | HTTP API |
|:-----|:-----------------|:---------|
| Cognito Authorizer | ✅ ネイティブ対応 | ✅ JWT Authorizer |
| リクエスト検証 | ✅ JSON Schema 検証 | ❌ なし |
| API キー管理 | ✅ 対応 | ❌ なし |
| 料金 | $3.50/100万リクエスト | $1.00/100万リクエスト |
| キャッシュ | ✅ 対応 | ❌ なし |

**REST API を選択した理由**:
1. **リクエスト検証**: JSON Schema でバリデーションをAPI Gateway層で実施 → Lambda の処理負荷軽減
2. **Cognito統合**: 設定のみで認証完了、Lambda側でのJWT検証コード不要
3. **将来の拡張性**: API キー管理、使用量プラン、キャッシュなど

**料金差（$2.50/100万リクエスト）は、個人利用規模では月額数十円の差であり、機能性を優先**
