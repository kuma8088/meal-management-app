# 要件定義書

## はじめに

本システムは、AWS サーバレスアーキテクチャを活用した食事管理アプリケーションです。ユーザーは LINE またはブラウザから食事を登録し、カロリーや PFC（タンパク質・脂質・炭水化物）バランスを自動計算できます。また、ユーザーの身体情報と活動レベルに基づいて基礎代謝と目標カロリーを算出し、Amazon Bedrock Claude を活用して 1 日の食事に対する総評とアドバイスを自動生成します。

## 用語集

- **システム**: 食事管理アプリケーション全体
- **ユーザー**: アプリケーションを利用する個人
- **食事記録**: ユーザーが登録した食事の情報（日時、食品、量など）
- **食品マスタ**: 食品名とその栄養情報（カロリー、タンパク質、脂質、炭水化物）を保持するデータベース
- **日本食品標準成分表**: 文部科学省が公開する日本の食品の栄養成分データベース
- **Open Food Facts**: オープンソースの食品データベース
- **食品マスタ CSV**: S3 に保存された食品マスタの完全なデータセット
- **PFC**: タンパク質（Protein）、脂質（Fat）、炭水化物（Carbohydrate）の略称
- **BMR**: 基礎代謝率（Basal Metabolic Rate）
- **TDEE**: 総消費カロリー（Total Daily Energy Expenditure）
- **目標カロリー**: ユーザーの活動レベルと体重目標を考慮した 1 日の推奨摂取カロリー
- **体重目標**: ユーザーが設定する増量、維持、減量のいずれかの目標
- **目標時期**: ユーザーが体重目標を達成したい期日
- **総評アドバイス**: Amazon Bedrock Claude が生成する 1 日の食事に対する評価とアドバイス
- **LINE クライアント**: LINE Messaging API を通じてアクセスするインターフェース
- **JAN コード**: 日本の商品バーコード規格（Japanese Article Number）
- **ブラウザクライアント**: Web ブラウザを通じてアクセスするインターフェース

## 要件

### 要件 1: ユーザー認証とデータ管理

**ユーザーストーリー:** ユーザーとして、自分のデータを安全に管理したいので、個人ごとに食事記録が分離されるようにしたい

#### 受入基準

1. WHEN ユーザーが LINE クライアントからアクセスする THEN システムは LINE User ID を使用してユーザーを識別する
2. WHEN ユーザーがブラウザクライアントからアクセスする THEN システムは Amazon Cognito を使用してユーザーを認証する
3. WHEN 食事記録が作成される THEN システムは認証されたユーザー ID と関連付けて保存する
4. WHEN ユーザーが食事記録を取得する THEN システムは自分自身の記録のみを返す
5. THE システムは未認証のリクエストを拒否する

### 要件 2: 食品マスタ管理

**ユーザーストーリー:** システム管理者として、正確な栄養計算を提供したいので、食品マスタを管理できるようにしたい

#### 受入基準

1. WHEN システムが初期化される THEN システムは日本食品標準成分表と Open Food Facts からデータを取得して DynamoDB に登録する
2. WHEN 初期データ取り込みが実行される THEN システムは Python スクリプトまたは Lambda 関数を使用してデータを処理する
3. WHEN 食品マスタデータが DynamoDB に登録される THEN システムは同じデータを CSV 形式で S3 バケットに保存する
4. WHEN ユーザーが食品を検索する THEN システムは食品マスタから該当する食品リストを返す
5. THE システムは食品マスタに食品名、カロリー（100g あたり）、タンパク質（g）、脂質（g）、炭水化物（g）を保持する

### 要件 3: 食品マスタの AI 検索とキャッシング

**ユーザーストーリー:** ユーザーとして、DynamoDB に存在しない食品でも栄養情報を取得したいので、Bedrock が S3 の食品マスタ CSV を参照して近似値を提供できるようにしたい

#### 受入基準

1. WHEN ユーザーが食品を検索し、DynamoDB に該当データが存在しない THEN システムは Bedrock Claude に検索をリクエストする
2. WHEN Bedrock が検索リクエストを受信する THEN システムは S3 バケットに保存された食品マスタ CSV へのアクセス権限を Bedrock に提供する
3. WHEN Bedrock が S3 の食品マスタ CSV にアクセスする THEN システムは類似する食品の栄養情報を検索する
4. WHEN Bedrock が類似食品を見つける THEN システムはその栄養情報を AI 検索結果としてマークして DynamoDB に保存する
5. WHEN AI 検索結果が DynamoDB に保存される THEN システムはデータソースフィールドに「AI_GENERATED」フラグを設定する
6. WHEN 同じ食品が再度検索される THEN システムは DynamoDB のキャッシュされた結果を返し、Bedrock API を呼び出さない
7. WHEN Bedrock が類似食品を見つけられない THEN システムは手動入力を促すメッセージを返す

### 要件 4: ブラウザでの食品検索

**ユーザーストーリー:** ユーザーとして、ブラウザから正確に食品を登録したいので、食品名や JAN コードで検索して食品を選択できるようにしたい

#### 受入基準

1. WHEN ユーザーがブラウザで食品名を入力する THEN システムは部分一致で食品マスタを検索し、候補リストを表示する
2. WHEN ユーザーがブラウザで JAN コードを入力する THEN システムは完全一致で食品マスタを検索し、該当商品を表示する
3. WHEN 検索結果が複数ある THEN システムは食品名、カロリー、PFC 情報を含むリストを表示する
4. WHEN ユーザーが検索結果から食品を選択する THEN システムは選択された食品の詳細情報を表示し、量の入力を促す
5. WHEN 検索結果が見つからない THEN システムは手動入力オプションまたは AI 検索オプションを提示する

### 要件 5: バーコード読み取り機能

**ユーザーストーリー:** ユーザーとして、商品パッケージから簡単に食品情報を登録したいので、LINE で食品バーコードの写真を送信して自動的に食品を検索できるようにしたい

#### 受入基準

1. WHEN ユーザーが LINE Bot に画像を送信する THEN システムは画像データを受信する
2. WHEN 画像データが受信される THEN システムは画像認識サービスを使用してバーコードから JAN コードを抽出する
3. WHEN JAN コードが抽出される THEN システムは食品マスタデータベースで該当する商品を検索する
4. WHEN 該当商品が見つかる THEN システムは商品名と栄養情報をユーザーに提示し、登録確認を求める
5. WHEN 該当商品が見つからない THEN システムは手動入力を促すメッセージを返信する
6. WHEN バーコード読み取りが失敗する THEN システムはエラーメッセージを返信し、再送信または手動入力を促す

### 要件 6: 食事登録

**ユーザーストーリー:** ユーザーとして、食事を簡単に記録したいので、LINE またはブラウザから食事情報を登録できるようにしたい

#### 受入基準

1. WHEN ユーザーが LINE クライアントから食事情報を送信する THEN システムは食事記録を作成し、データベースに保存する
2. WHEN ユーザーがブラウザクライアントから食事情報を入力する THEN システムは食事記録を作成し、データベースに保存する
3. WHEN 食事記録が作成される THEN システムは食品マスタを参照して栄養情報を自動的に計算する
4. WHEN 食事記録の保存が成功する THEN システムはユーザーに確認メッセージを返す
5. WHEN 食事記録の保存が失敗する THEN システムはエラーメッセージをユーザーに通知する

### 要件 7: 栄養情報の自動計算

**ユーザーストーリー:** ユーザーとして、栄養管理を簡単にしたいので、食事のカロリーと PFC が自動的に計算されるようにしたい

#### 受入基準

1. WHEN 食事記録が作成される THEN システムは食品マスタを使用してカロリーを計算する
2. WHEN 食事記録が作成される THEN システムは食品マスタを使用してタンパク質量を計算する
3. WHEN 食事記録が作成される THEN システムは食品マスタを使用して脂質量を計算する
4. WHEN 食事記録が作成される THEN システムは食品マスタを使用して炭水化物量を計算する
5. WHEN 複数の食品が 1 つの食事に含まれる THEN システムは各食品の栄養情報を合計する

### 要件 8: 基礎代謝と TDEE の算出

**ユーザーストーリー:** ユーザーとして、自分に適した食事量を知りたいので、身体情報に基づいた基礎代謝と総消費カロリーが算出されるようにしたい

#### 受入基準

1. WHEN ユーザーが年齢、身長、体重、性別を登録する THEN システムは Harris-Benedict 式を使用して BMR を計算する
2. WHEN ユーザーが活動レベルを選択する THEN システムは BMR に活動係数を乗じて TDEE を算出する
3. WHEN ユーザープロフィールが更新される THEN システムは自動的に BMR と TDEE を再計算する
4. THE システムは活動レベルとして「ほとんど運動しない」「軽い運動」「中程度の運動」「激しい運動」「非常に激しい運動」の 5 段階を提供する

### 要件 9: 体重目標管理と栄養計画

**ユーザーストーリー:** ユーザーとして、体重目標を達成したいので、増量・維持・減量の目標と期日を設定し、必要な栄養摂取量と運動量を確認できるようにしたい

#### 受入基準

1. WHEN ユーザーが体重目標を設定する THEN システムは「増量」「維持」「減量」の 3 つの選択肢を提供する
2. WHEN ユーザーが目標体重と目標時期を入力する THEN システムは現在の体重との差分と期間から 1 日あたりの必要カロリー調整量を計算する
3. WHEN カロリー調整量が計算される THEN システムは TDEE に調整量を加算または減算して目標カロリーを算出する
4. WHEN 目標カロリーが算出される THEN システムは推奨される PFC バランスを計算する
5. WHEN ユーザーが目標達成に必要な情報を要求する THEN システムは 1 日の目標カロリー、推奨 PFC、推奨運動量を表示する
6. WHEN 目標時期が非現実的である THEN システムは健康的な減量・増量ペース（週あたり 0.5kg 以内）を推奨する警告を表示する

### 要件 10: 1 日の総評アドバイス生成

**ユーザーストーリー:** ユーザーとして、食事改善のヒントを得たいので、AI による 1 日の食事の総評とアドバイスを受け取りたい

#### 受入基準

1. WHEN ユーザーが 1 日の総評をリクエストする THEN システムはその日のアドバイス生成回数を確認する
2. WHEN アドバイス生成回数が 1 日 2 回未満である THEN システムはその日の全食事記録を集計する
3. WHEN アドバイス生成回数が 1 日 2 回に達している THEN システムは利用制限メッセージを返す
4. WHEN 食事記録の集計が完了する THEN システムは総カロリー、総 PFC、目標カロリーとの差分を計算する
5. WHEN 栄養データが準備される THEN システムは Amazon Bedrock Claude API を呼び出してアドバイスを生成する
6. WHEN Bedrock API が応答を返す THEN システムは生成されたアドバイスを 300 文字以内に制限してユーザーに提示する
7. WHEN 生成されたアドバイスが 300 文字を超える THEN システムはアドバイスを 300 文字に切り詰める
8. WHEN アドバイスが正常に生成される THEN システムはユーザーの 1 日のアドバイス生成回数を 1 増やす
9. WHEN Bedrock API 呼び出しが失敗する THEN システムは基本的な統計情報のみを表示し、エラーを記録する

### 要件 11: LINE 連携

**ユーザーストーリー:** ユーザーとして、日常的に使う LINE から簡単に記録したいので、LINE Messaging API と連携したい

#### 受入基準

1. WHEN ユーザーが LINE Bot にメッセージを送信する THEN システムは Webhook を通じてメッセージを受信する
2. WHEN メッセージが食事登録の形式に一致する THEN システムは食事記録を作成する
3. WHEN メッセージが総評リクエストの形式に一致する THEN システムは 1 日の総評を生成して返信する
4. WHEN メッセージの形式が不明である THEN システムは使用方法のヘルプメッセージを返信する
5. THE システムは LINE Messaging API を使用してユーザーに応答を送信する

### 要件 12: データの永続化

**ユーザーストーリー:** ユーザーとして、過去の食事記録を参照したいので、データが永続的に保存されるようにしたい

#### 受入基準

1. THE システムは Amazon DynamoDB を使用してユーザープロフィール、食事記録、食品マスタを保存する
2. WHEN データが保存される THEN システムはデータの整合性を検証する
3. WHEN ユーザーが過去の記録を要求する THEN システムは指定された期間の食事記録を取得する
4. WHEN データ取得が失敗する THEN システムはエラーを記録し、ユーザーに通知する

### 要件 13: API エンドポイント

**ユーザーストーリー:** 開発者として、システムを拡張可能にしたいので、明確に定義された API エンドポイントを提供したい

#### 受入基準

1. THE システムは AWS API Gateway と AWS Lambda を使用して RESTful API を提供する
2. WHEN API リクエストが受信される THEN システムはリクエストの形式を検証する
3. WHEN 検証が失敗する THEN システムは適切な HTTP ステータスコードとエラーメッセージを返す
4. THE システムは食事記録の作成、取得、更新、削除のエンドポイントを提供する
5. THE システムはユーザープロフィールの作成、取得、更新のエンドポイントを提供する
6. THE システムは総評アドバイス生成のエンドポイントを提供する

### 要件 14: エラーハンドリングとロギング

**ユーザーストーリー:** システム管理者として、問題を迅速に特定したいので、適切なエラーハンドリングとロギングが実装されるようにしたい

#### 受入基準

1. WHEN システムエラーが発生する THEN システムはエラーの詳細を Amazon CloudWatch Logs に記録する
2. WHEN 外部 API 呼び出しが失敗する THEN システムはリトライロジックを実行する
3. WHEN リトライが全て失敗する THEN システムはユーザーに適切なエラーメッセージを返す
4. THE システムは各 Lambda 関数の実行時間、成功率、エラー率をメトリクスとして記録する
5. WHEN 重大なエラーが発生する THEN システムは管理者に通知する

### 要件 15: インフラストラクチャ管理

**ユーザーストーリー:** インフラエンジニアとして、インフラを再現可能かつ管理しやすくしたいので、Terraform を使用してインフラをコード化したい

#### 受入基準

1. THE システムは Terraform を使用してすべての AWS リソースを定義する
2. WHEN Terraform が実行される THEN システムは DynamoDB テーブル、Lambda 関数、API Gateway、Cognito ユーザープール、IAM ロールを作成する
3. WHEN インフラ変更が必要になる THEN 開発者は Terraform コードを更新して適用する
4. THE システムは Terraform state ファイルを S3 バケットに保存し、DynamoDB でロックを管理する
5. THE システムは環境変数と設定値を Terraform 変数として管理する
